# Agent 框架对比的本质：不是比功能，是比"隐藏了什么"

> 前两篇我们深入了 LangGraph 和多 Agent 范式。这一篇是 Phase 3 的收官——不谈单个框架，谈比较框架的方法论。读完这篇文章，你收获的不是"该选哪个框架"的答案，而是一套评估任何 Agent 框架的思考工具。

---

## 为什么大多数框架对比毫无价值

你在网上看到的框架对比文章通常长这样：

```
| 功能 | A框架 | B框架 | C框架 |
|------|-------|-------|-------|
| 工具调用 | ✓ | ✓ | ✓ |
| 多Agent | ✓ | ✓ | ✗ |
| RAG支持 | ✓ | ✓ | ✓ |
```

这种表格的问题在哪？**它比较的是功能是否存在，而不是功能如何实现。** "多 Agent 支持"打勾——但 A 框架的多 Agent 是图节点间的条件路由，B 框架的多 Agent 是角色间的隐式上下文传递。功能名相同，背后的设计哲学完全不同。

我在这三篇文章中反复强调一个观点：

> **比较框架的正确姿势不是比"有什么功能"，而是比"框架隐藏了什么，暴露了什么，以及当你的需求超出框架预设时，你有没有退路。"**

这篇文章就用这个框架来做一个真正的对比。

---

## 分析维度一：框架隐藏了什么？

框架的本质是抽象。抽象的价值在于隐藏复杂度——你不需要知道 HTTP 协议细节就能用 `requests.get(url)`。但抽象的危险在于：**隐藏的东西恰恰是你需要控制的东西时，框架就变成了障碍。**

我们分析三个框架各自隐藏了什么：

**LangGraph 隐藏了：**
- 执行循环（你不用写 while）
- 状态持久化（checkpointer 每步自动保存）
- 检查点管理（时间旅行、分支分叉）

LangGraph **没有**隐藏的：
- State 的结构（你必须自己定义 TypedDict）
- 路由逻辑（你必须写条件边函数）
- 图的结构（你必须 add_node + add_edge）

隐藏的刚好是"机械性"的工作（保存状态、管理循环），暴露的刚好是"设计性"的工作（定义数据模型、设计控制流）。这是一个很好的平衡——**框架替你做重复劳动，但不替你做设计决策。**

**CrewAI 隐藏了：**
- State 管理（上下文自动从上一个 Task 传给下一个）
- Agent 协调（Sequential / Hierarchical 自动调度）
- 消息格式（Agent 间的通信框架内部处理）

CrewAI **没有**隐藏的：
- 角色定义（你必须写 role + goal + backstory）
- 任务描述（你必须写 description + expected_output）
- 流程选择（你选 Sequential 还是 Hierarchical）

这里有个微妙的问题：**CrewAI 隐藏的东西恰好是在复杂场景下你最需要控制的东西。** 比如上下文传递——CrewAI 自动把上一个 Task 的输出给下一个 Task，但你无法控制"传什么、不传什么"。如果上一个 Task 输出了 2000 字，你不想全文传递给下一个 Agent——对不起，框架帮你传了，你不能截断。

这就是"抽象泄露"——当你的需求超出框架预设时，你被框架困住了。

**Claude SDK 隐藏了：**
- API 格式（message 结构、tool schema）
- 流式传输
- 错误重试

Claude SDK **没有**隐藏的：
- **一切。** 循环、状态、错误处理、编排——全部是你自己写。

隐藏最少 = 控制最多 = 代码量最大。这是三种方案中最"低级"的抽象，但也是最灵活的一个——它永远不会成为你的障碍，因为你可以替换任何部分。

**核心洞察**：

```
隐藏什么 = 框架替你做的决策
暴露什么 = 你需要做的决策

好的框架：隐藏机械性工作，暴露设计性决策
差的框架：隐藏设计性决策，让你在遇到边界情况时束手无策
```

## 分析维度二："逃生舱"测试

"逃生舱"（Escape Hatch）是我自己用的术语——**当你的需求超出了框架的设计范围，你有没有办法绕过框架，直接控制底层行为？**

我用三个真实场景来测试三个框架的逃生舱：

### 测试 1：检索质量不合格时需要自动重新搜索

**LangGraph**：在 `doc_grader` 节点后加一个条件边，相关性不达标 → 走 `query_rewriter` 节点 → 回到 `retriever`。改一行图配置。逃生舱：★★★★★

**CrewAI**：Sequential 流程不支持条件跳转。你只能在 Task description 里写"如果信息不足，尝试不同关键词"——靠 LLM 自觉。框架不提供"回到上一步"的机制。逃生舱：★☆☆☆☆

**Claude SDK**：`if quality < threshold: rewrite_and_retry()`。就是一行 if。逃生舱：★★★★★

### 测试 2：任务做到一半需要人类审批

**LangGraph**：在关键节点调用 `interrupt()`，框架暂停图执行，等待 `Command(resume=value)`。可以暂停三天。逃生舱：★★★★★

**CrewAI**：不支持任务中间暂停。你只能等整个 Crew 跑完再人工审查输出。逃生舱：☆☆☆☆☆

**Claude SDK**：自己写一个 `wait_for_human()` 函数。可以做，但检查点持久化要自己实现。逃生舱：★★★☆☆

### 测试 3：某步执行失败后切换备用策略

**LangGraph**：条件边 + 多个备用节点。`route_on_error(state) → "fallback_node"`。逃生舱：★★★★★

**CrewAI**：框架没有错误恢复机制。Agent 失败 = Task 失败。逃生舱：★☆☆☆☆

**Claude SDK**：`try: ... except: fallback_strategy()`。标准 Python 异常处理。逃生舱：★★★★★

### 逃生舱总评

| 场景 | LangGraph | CrewAI | Claude SDK |
|------|-----------|--------|------------|
| 条件重试 | ★★★★★ | ★★☆☆☆ | ★★★★★ |
| 人类审批 | ★★★★★ | ☆☆☆☆☆ | ★★★☆☆ |
| 错误恢复 | ★★★★★ | ★☆☆☆☆ | ★★★★★ |

LangGraph 在"超出简单线性流程"的场景中优势明显——因为它的图结构原生支持条件、循环、暂停。Claude SDK 什么都能做，但你要自己建。CrewAI 在这些需求面前设计不足——不是 bug，是设计范围不同。

## 分析维度三：代码量 vs 控制力

这不是一个道德判断——"控制力高就是好"或"代码量少就是好"。不同的场景需要不同的权衡。

你花时间写的每一行代码，换来的是你对系统行为的确定性和掌控力。

- **CrewAI**：60 行。放弃控制，换取速度。适合"我需要快速看到多 Agent 能不能协作"的场景。
- **LangGraph**：120 行。声明式控制，换取可维护性。适合"这个 Agent 六个月后还需要改"的场景。
- **Claude SDK**：200 行。完全控制，换取灵活性。适合"我不确定未来会有什么需求，我需要最大自由度"的场景。

这三个数字不是精确的，但是方向的：**代码量 = 控制力 × 灵活性。你不可能同时拥有"最少的代码"和"最强的控制"。**

## 一个通用的评估框架

忘掉这三个框架的具体名字。当你面对任何一个新的 Agent 框架（下个月又会出一个新的），问四个问题：

### 问题一：这个框架的"核心隐喻"是什么？

LangGraph 的核心隐喻是"图"——节点和边。
CrewAI 的核心隐喻是"组织"——角色和流程。
Claude SDK 的核心隐喻是"工具"——API 和函数调用。

**为什么这很重要？** 因为核心隐喻决定了框架适合解决什么问题。如果你拿到一个"用角色协作"的问题，CrewAI 的隐喻让你用角色来表达解——自然、直观。如果你用 LangGraph 解同样的问题——你需要把"角色"翻译成"节点"，把"协作"翻译成"边"——生硬、绕路。

**选择一个隐喻匹配你问题的框架，比选择"功能最多"的框架重要得多。**

### 问题二：框架隐藏了什么？暴露了什么？

- 隐藏的是机械性工作还是设计性决策？
- 你有没有遇到"框架替你做了你不想要的决定"的情况？

规则：**隐藏 = 不可控。** 框架隐藏得越多，你在边界情况下的退路越少。但隐藏得越多，你写的代码也越少。这是 tradeoff。

### 问题三：逃生舱在哪？

当你的需求超出了框架的设计范围：
- 能不能绕过框架直接控制底层？
- 能不能替换框架的一部分而不重写全部？

LangGraph 的逃生舱：每个节点是普通 Python 函数，可以绕过图直接调 LLM。
CrewAI 的逃生舱：Agent 可以调任意 Python 函数，但框架的调度逻辑不可替换。
Claude SDK 的逃生舱：它就是逃生舱——你本来就在底层。

### 问题四：这个框架的"天花板"在哪？

每个框架都有一个它解决不了的问题类型：
- CrewAI 解决不了"需要条件跳转"的问题
- LangGraph 对"一个 API 调用就能搞定"的问题是过度设计
- Claude SDK 解决不了"我想要声明式控制流"的问题（它本身就是命令式的）

**理解框架的"不适配场景"比理解它的"最佳场景"更重要。** 因为技术选型的正确率取决于你避开了多少踩坑场景，而不是你找到了多少完美匹配。

## 关于"该选哪个框架"的诚实回答

每次讲完三个框架，都会被问："所以我该用哪个？"

我的回答是：**取决于你接下来三个月要做什么。**

**如果你在验证一个想法**——Agent 协作是否可行？多 Agent 分析是否比单 Agent 好？——用 CrewAI。20 分钟能跑通，结果本身就是答案。不必为验证想法建一座图的大厦。

**如果你在构建一个生产系统**——需要维护六个月以上、需要可观测性、需要故障恢复——用 LangGraph。显式 State + 声明式控制流 + Checkpointer 是你未来调试时的救命稻草。

**如果你不确定未来会有什么需求**——或者你需要在每一步都做精确的决策——用 Claude SDK 或直接手写。不引入框架概念，保持最大自由度。

**如果你的项目在成长**——从原型到生产——我的建议是"分层组合"：

```
原型阶段   → CrewAI（验证可行性，分钟级）
MVP 阶段   → LangGraph（加控制流 + checkpointing）
生产阶段   → LangGraph（编排）+ Claude SDK / MCP（工具和安全）
```

这不是三个选一个的问题。这是架构演变的问题。

## Phase 3 结语

从 Phase 1 手写 ReAct Agent，到 Phase 2 构建 RAG 全链路，到 Phase 3 用三个框架实现同一个任务、做架构层面的终极对比——你经历了从"会调 API"到"理解框架设计"的跃迁。

Phase 3 的核心收获不是"学会了三个框架的 API"——API 查文档就会。而是：

1. **Agent 工作流不应该建模为 while 循环**。图编排（LangGraph）用显式控制流取代了隐式循环，换来了可调试性、可持久化、人机协作。

2. **多 Agent 协作有三种根本不同的范式**。图编排（控制流中心）、角色扮演（组织中心）、自主循环（Agent 中心）。不是"哪个更好"，是"哪个更适合你的问题"。

3. **比较框架的正确方法不是比功能表**。而是问四个问题：核心隐喻是什么？隐藏了什么？逃生舱在哪？天花板在哪？这套思考工具适用于任何新框架。

4. **生产系统往往组合使用**。编排层用 LangGraph，工具层用 Claude SDK / MCP，原型层用 CrewAI。不是三选一，是分层架构。

Phase 4 将在此基础上深入：高级记忆系统（短期/长期/工作记忆）、多 Agent 通信模式（Swarm/Handoff/Broadcast）、MCP 协议实战、安全纵深防御。
